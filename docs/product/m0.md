# M0: the first product milestone

Date: 2026-09-07. Status: defined; implementation tracked stage by stage in
`PROJECT_STATE.md`.

## The candidate workflow, challenged

The owner's candidate: lecturer lands on a polished site, discovers
activities, signs in, selects activities, creates a lesson, adds
instructions and questions, previews it, publishes one student link, student
completes it.

Everything in that list is in M0 except **sign-in**, which is deliberately
left out:

- Signing in exists to save something server-side. In M0 the lesson *is* the
  link, so there is nothing to save that the lecturer does not already hold.
- Accounts bring infrastructure, a privacy policy, a data-processing story
  and support obligations before a single lecturer has said the builder is
  worth using.
- Without accounts the whole of M0 ships on the existing GitHub Pages
  deployment with the existing gates, and the free layer stays as private as
  it is today.

Also left out on purpose: assignment or completion tracking, any aggregate
of student responses, payments, an admin system, and AI assistance.

## The vertical slice

> A methods lecturer finds the p-value simulator by searching "p-value",
> reads how to run it from the front, adds the Simplified twin and the power
> lab to a lesson, writes two instructions and two questions, previews it on
> a phone, copies one link into Moodle. A student opens the link on a phone,
> works through both activities with the lecturer's instructions beside
> them, answers the two questions, and downloads their answers to bring to
> the seminar.

## Stages, each a checkpoint commit with gates green

### Stage 1: honest site

Fix the eight recorded documentation defects plus D9 (teaching notes not on
the site), so that the product work starts from a site that tells the truth
about itself.

Acceptance criteria
- No page or document says tools are in preparation, being written, or
  number twelve.
- `check-all.py` green.

### Stage 2: embed mode

Acceptance criteria
- `?embed=1` on any of the 150 activity pages hides site header, navigation,
  breadcrumbs, footer, previous/next strip and lecturer export controls, and
  changes nothing else about the activity.
- Without the parameter every page is byte-for-byte unchanged in behaviour.
- The embedded page posts its content height to its parent.
- The 75 `standalone.html` exports are unaffected (`--check` passes).
- Browser smoke test extended with embedded loads of one page per edition.

### Stage 3: library

Acceptance criteria
- `library/index.html` lists all 150 activities from the two catalogues,
  with search and filters (module, edition, duration, difficulty), keyboard
  operable, usable at 320px and projector widths. Interaction type is not a
  facet: the catalogues hold several hundred free-text values, so it is
  covered by search instead.
- Each result links to the activity, its twin and its notes page.
- `library/activity.html` renders an activity's metadata and its
  `teaching-notes.md` as accessible HTML, with a link to open the activity.
- Works on GitHub Pages and on a local HTTP server; degrades to a clear
  message on `file://`.
- Home page links to the library as the primary discovery route.

### Stage 4: lesson builder

Acceptance criteria
- `lessons/build.html`: title, intro, ordered steps of three kinds
  (activity, note, question); reorder and remove; add activities from the
  library or by search inside the builder.
- Draft autosaves to `localStorage`; "Clear draft" removes it; the page says
  where the draft lives.
- "Preview" shows the player with the current lesson.
- "Get student link" produces a URL with the lesson in the fragment,
  shows its length, warns above 2,000 characters, and offers copy.
- "Download lesson file" / "Open lesson file" round-trips the JSON.
- Lesson JSON validates against `data/lessons/schema.json`
  (a new gate in `check-all.py` validates the curated lessons).

### Stage 5: lesson player

Acceptance criteria
- `lessons/index.html#l=…` renders title, intro and steps; activities embed
  in frames with the lecturer's instructions beside them; questions take
  short or long answers.
- Answers are held in memory only; "Download my answers" and "Copy my
  answers" produce plain text; the page states that nothing is sent anywhere.
- An unresolvable activity reference shows a clear message and the rest of
  the lesson still works.
- Fully keyboard operable, focus management between steps, live region for
  step changes, reduced motion honoured, 320px and projector widths.
- Browser smoke test covers a curated lesson.

### Stage 6: curated lessons and polish

Acceptance criteria
- Three author-written lessons under `data/lessons/` demonstrate the format
  (one per teaching setting: lecture demonstration, seminar, revision).
- Home page rewritten for lecturers: what it is, find an activity, build a
  lesson, the two editions explained in one paragraph, and the free promise.
- `PROJECT_STATE.md` records the milestone as verified.

## Non-goals for M0

Accounts, storage, tracking, payments, admin, LTI, AI, new activities, any
change to how an activity behaves, any change to the two editions' visual
languages.

## Definition of done

All six stages' acceptance criteria met, `check-all.py --lint --browser`
green, and the vertical slice above walked through end to end in a browser
at phone and desktop widths, with the walkthrough recorded in
`PROJECT_STATE.md`.
